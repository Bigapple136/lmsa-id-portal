## Design-specificity verdict

**Not impeccable — the surface is credible, the substrate is not.** The mapper reads as purpose-built for LMSA card production rather than as a generic drag-and-drop canvas: the Auto-Map confirmation dialog, per-side field assignment, mm annotations, the QR corner-radius caution, and the live `CardCanvas` preview fed from live state are all decisions someone made on purpose about *this* product.

The failure is one level down. This is a precision instrument whose measurements and previews do not match what it produces. Two independent editor↔renderer disagreements and a swapped card dimension mean an admin can carefully align a field in the mapper and print it somewhere else. Craft polish on top of that is decoration.

## Assessment A — design review findings

### What is working

- **The live preview is architecturally right.** `CardCanvas` is fed from the mapper's own `frontLayout`/`backLayout` state (`LayoutMapper.jsx:1255-1268`), so preview can never drift from what Save persists. Most tools of this kind build a second, divergent renderer.
- **Auto-Map is staged, not applied.** `openAutoMap` builds a proposal and shows a field→box table for confirmation (`LayoutMapper.jsx:520-546`, dialog at `1272-1340`) with `role="dialog"`, `aria-modal`, and labelled/described ids. That is the correct pattern for a bulk overwrite.
- **The hydration races were thought about.** `sidesInitialized` and `layoutInitialized` refs (`LayoutMapper.jsx:225-260`) with server data spread last on first hydration and local state authoritative afterwards is the right resolution of the async-`initialLayout` problem, and the comments explain it.
- **Sample data is honestly synthetic and labelled.** `PREVIEW_STUDENT` (`LayoutMapper.jsx:17-26`) is fictional, comment-flagged "never real student data", and the UI says "sample data".
- **Save is conservative.** Only sides with an uploaded template are sent, and `VALID_LAYOUT_FIELDS` filters config keys out of the payload (`LayoutMapper.jsx:412-436`).

### P0-1 — Every millimetre readout in the property panel is wrong

Evidence:
- `layoutConstants.js:9-10` defines `CARD_WIDTH_MM = 85.6`, `CARD_HEIGHT_MM = 54` — CR-80 in **landscape**.
- The card is **portrait**: `CardCanvas.jsx:~295` sets `paddingTop: '158.5%'` with the comment "CR-80 aspect ratio (approx 1004/634)", the calibrated template is 590×1004 (`LayoutMapper.jsx:200`, `layoutConstants.js:3`), and every default layout in `CALIBRATED_LAYOUT_FRONT` is authored for a tall card.
- Those constants are multiplied by fractional coordinates at `LayoutMapper.jsx:1061`, `1078`, `1097`, `1113` to print "mm from left", "mm from top", "mm wide", "mm tall".

Impact: horizontal distances are inflated ~1.59× and vertical distances shrunk ~0.63×. A photo frame the admin measures on a printed card at 40mm wide is reported by the tool as 63mm. The mm annotations exist precisely so an admin can reconcile the mapper with a physical card or a print spec; as shipped they guarantee the reconciliation fails, and they fail *confidently*, to one decimal place.

Recommendation: swap to portrait (`CARD_WIDTH_MM = 53.98`, `CARD_HEIGHT_MM = 85.6`), or better, derive both from the detected template aspect and the CR-80 long edge so an admin who uploads a landscape template still gets true numbers. Add a unit assertion in `layoutConstants.js` tying mm ratio to the rendered aspect ratio.

### P0-2 — The editor chip and the renderer disagree on vertical anchor for non-centered text

Evidence:
- `CardCanvas.jsx:238` sets `ctx.textBaseline = 'middle'` for **all** text, and draws at `ctx.fillText(text, xPos, pos.y * H)` (`:249`). `pos.y` is therefore always the vertical **center** of the glyph box.
- `LayoutMapper.jsx:790` computes the chip's top as `anchorTop = isImg || align !== 'center' ? pos.y : pos.y - chipH / 2`. The `align !== 'center'` branch treats `pos.y` as the chip's **top** edge.

Impact: any text field whose `textAlign` is `left` or `right` — the default is `left` (`LayoutMapper.jsx:788`) — is drawn in the editor roughly half a line-height below where the card actually prints it. The admin aligns the wrong thing. This is the single most damaging defect in a WYSIWYG tool: the "what you see" and the "what you get" are different documents, and the error is small enough to be attributed to eyeballing rather than to the tool.

Note the same conditional conflates alignment (horizontal) with baseline (vertical); the horizontal half of the expression on the line above (`anchorLeft`, `:788-789`) is correct. Only the vertical term is broken.

Recommendation: `anchorTop = isImg ? pos.y : pos.y - chipH / 2`, unconditionally, and add a rendering-parity test that asserts, for each of left/center/right, that the chip rectangle's center equals the coordinate `CardCanvas` would draw at.

### P1-1 — The live preview cannot show the three fields whose placement is hardest

Evidence:
- `PREVIEW_STUDENT` (`LayoutMapper.jsx:17-26`) supplies only text values: no `photo_url`, no `signature_url`, no `qr_url`.
- `CardCanvas` skips each image field when its URL is absent — `if (!student.photo_url) continue` (`:159`), `if (!student.signature_url) continue` (`:194`), `if (!student.qr_url) continue` (`:218`).

Impact: the "what students see" panel silently omits photo, signature, and QR — exactly the fields with width/height/corner-radius controls, exactly the ones that clip, overflow the template frame, or break scanning. The mapper's only ground-truth view is blind in the region where the mapper's editing chips are least trustworthy.

Recommendation: ship three small bundled placeholder assets (a neutral portrait silhouette, a scrawl, a static demo QR), point `PREVIEW_STUDENT` at them, and label them as sample assets in the caption already present.

### P1-2 — No unsaved-changes state anywhere, and Reset is an unconfirmed destructive action

Evidence:
- There is no dirty flag in the component (`grep -n "dirty\|unsaved"` returns nothing across `LayoutMapper.jsx`).
- Reset replaces the whole side in one click with no confirmation: `onClick={() => { setLayout({ ...defaultLayout }); setSelected(null) }}` (`LayoutMapper.jsx:599-604`).
- `applyAutoMap` merges a whole proposal over live state (`:548-554`).
- `switchSide` (`:562-567`) and tab changes in `AdminDashboard.jsx:2549` unmount or swap away with no guard; there is no `beforeunload` handler.
- Version history only lists **saved** versions (`loadHistory`, `:445-456`), so it cannot recover unsaved work.

Impact: an admin who spends twenty minutes nudging a front layout, then clicks Reset, switches to Back, or navigates away, loses all of it with no warning and no recovery path. The two-and-a-half-second toast is the only feedback the system ever gives about persistence state.

Recommendation: track a dirty flag per side; badge the Save button and the Front/Back tabs when dirty; route Reset and Auto-Map apply through the existing `ConfirmDialog` (already imported in `AdminDashboard.jsx:13`); add a `beforeunload` guard and an in-app confirm on tab switch.

### P1-3 — Corner radius previews as a different shape than it prints

Evidence:
- Mapper chip: `borderRadius: \`${Math.min((pos.borderRadius || 0) / Math.min(pos.width, pos.height), 0.5) * 100}%\`` (`LayoutMapper.jsx:812-814`). A single percentage on a non-square box resolves per-axis in CSS, producing an **elliptical** corner.
- Renderer: `tracePath(ctx, px, py, pw, ph, (pos.borderRadius || 0) * W)` (`CardCanvas.jsx:174`) — a **circular** radius in pixels, scaled by card width only.

Impact: the two shapes coincide only when the field is square. For the typical portrait photo frame the editor shows a noticeably different curve than the card prints, which is precisely the case the feature was added for ("match a rounded template frame").

Also in this control: the help copy branch is inverted in tone — for `selected === 'qr'` it opens "Rounds the photo/image corners…" before warning about QR (`LayoutMapper.jsx:1119-1124`). Lead with the warning on the QR branch.

Recommendation: give the chip `borderRadius: \`${pos.borderRadius * DISPLAY_W * zoom}px\`` (same pixel basis as the canvas, clamped identically), not a percentage.

### P1-4 — Auto-Map heuristics are forked in three places and have already diverged

Evidence:
- `buildSuggestedLayout` in `LayoutMapper.jsx:75-148` hardcodes its own `charEstimates` table (`:78-82`) rather than importing `EST_CHARS`, which the same file already imports (`:7`) and uses in `snapFieldToZone` (`:494`).
- The two tables agree today but are maintained independently, and `EST_CHARS` (`layoutConstants.js:176-189`) carries eight fields the local copy omits.
- The header comment on `buildSuggestedLayout` concedes a third copy: "Mirrors backend/utils/detectZones.js generateSuggestedLayout."
- The magic fit formula `Math.min(z.width / (chars * 0.62), z.height * aspect * 0.8, 0.12)` appears verbatim at `:103` and `:495`.

Impact: three implementations of "where should this field go" that must stay in lockstep for the client-side Auto-Map, the click-to-snap path, and the server's stored `suggested_layout_*` to agree. They will not. An admin who snaps a field into box 3 and an admin who Auto-Maps the same template can already get different font sizes for the same field the moment one table is edited.

Recommendation: extract one exported `fitTextToZone(zone, field, aspect)` and one `suggestLayout(zones, side, aspect)` into `layoutConstants.js` (or a shared `layoutMath.js`), import it in both frontend call sites, and make the backend the same module or a tested mirror with a fixture asserting parity.

### P1-5 — Silent failure paths present as confident negative facts

Evidence:
- Zone detection loads the template with `img.crossOrigin = 'anonymous'` (`LayoutMapper.jsx:277`); a storage host without permissive CORS fails `onerror` (`:293`) and the loop only clears `zonesLoading`.
- `detectZonesFromImage(...).catch(() => { /* detection failed */ })` (`:286-288`) discards the error entirely.
- With zero zones the UI states: "No field boxes detected. Drag each field to its spot…" (`:693`).
- `handleSave`'s catch collapses every failure — auth, validation, network — into "Failed to save layout." (`:433`).

Impact: "no boxes on your template" and "the browser could not read your template" are different problems with different fixes, and the tool reports the second as the first. The admin re-exports the template, or hand-places eleven fields, to work around a CORS header.

Recommendation: distinguish `error` from `empty`. On load/detection failure say so and name the likely cause; surface the server's `error` string on save failure (`AdminDashboard.jsx:648-652` already throws it, the mapper discards it).

## Persona red flags

- **Registrar preparing a new cohort template:** measures the printed card's photo window with a ruler, types the mm the tool asks for, and gets a frame 1.6× too wide. Nothing in the UI contradicts them.
- **Operator fine-tuning a left-aligned ID number:** aligns the chip perfectly against the template's printed rule, prints, finds the number sitting half a line high. Re-nudges by eye against the printed proof, permanently distrusting the editor.
- **Admin uploading a replacement template mid-session:** `layoutInitialized.current = false` (`LayoutMapper.jsx:243-246`) re-hydrates from the *previous* `initialLayout` prop and can overwrite in-progress edits with no notice.
- **Keyboard-only admin:** can tab to zones and chips and nudge with arrows (good), but gets no announcement of the resulting coordinate, cannot Escape out of the Auto-Map dialog, and receives no focus into it.
- **Admin on a 900px-wide tablet:** `.layout-columns` wraps (`index.css:4336-4342`) and the 260px canvas at 1.5× zoom is 390px with 8px chip labels — below any reasonable precision threshold for placing an 0.86mm nudge.

## Minor observations

- **Clamp/input mismatch:** drag and nudge clamp to `x ≤ 0.92`, `y ≤ 0.95` (`:342-343`, `:375-376`) while the numeric inputs accept `max="95"` for both (`:1055`, `:1072`). Two different ceilings for the same value, and neither accounts for the field's own width, so an image field can be positioned entirely off the card's right edge.
- **Nudge granularity:** one step, 1% (≈0.86mm horizontally on a real portrait card). No Shift-for-fine or Shift-for-coarse modifier — standard in every layout tool.
- **Emoji as system iconography:** 🎨 Front / 🔙 Back / ✨ Auto-Map / 🧩 / 🕑 / ⚙️ / 👆 (`:579`, `:585`, `:596`, `:872`, `:921`, `:1017`, `:1235`). 🔙 is a *navigational* back-arrow glyph used to label the reverse face of a card — wrong meaning, not just wrong style. This repeats P1 findings from the 2026-09-02 admin snapshot.
- **Toast timing:** every message clears at 2500ms (`:437`, `:474`, `:534`, `:553`), including errors, and the banner is not an `aria-live` region — a screen-reader user may never learn a save failed.
- **Zone labels:** `aria-label={\`Template box ${i + 1}…\`}` with no size, position, or "already occupied by X" context; on a template with a dozen detections this is a tab-stop maze.
- **Component size:** 1340 lines, twelve props, seventeen `useState` calls, ~90 inline style objects, no tests. The canvas editor, the field-side panel, the history panel, the property panel, and the Auto-Map dialog are five independently testable components living in one file.
- **Detection cost:** zones are re-detected from scratch on every side switch (`:271-300`, keyed on `templateUrl`) with no per-side cache.
- **`msg` and `activeZone` reset:** `switchSide` clears `selected`/`activeZone`/`autoMap` but leaves a stale `msg` from the other side on screen.
- **`objectFit: 'fill'`** on the template image (`:728`) will silently distort if `displayH` has not yet updated for a newly swapped template.
